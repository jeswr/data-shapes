The Shapes Constraint Language (SHACL) [[!shacl]] is a language for validating RDF graphs against a set of conditions. SHACL consists of SHACL Core and SHACL-SPARQL which covers advanced features that use SPARQL-based constraints. The syntax of SHACL is RDF.

This document defines the Compact Syntax for a subset of SHACL Core. The Compact Syntax offers an alternative notation to the general RDF-based notations for SHACL, aimed at human editors and readers.

It includes proposed support for RDF 1.2 [[rdf12-concepts]]: triple terms, reifiers and reified triples, directional language tags, and the SHACL 1.2 constraint components that build on them. Every new syntactic form is defined by a normative mapping to RDF 1.2 triples; the additions are marked 1.2 throughout.

This specification was started by the RDF Data Shapes WG, was continued within the SHACL Community Group, and is now being picked up by the Data Shapes WG.

The support for RDF 1.2 [[rdf12-concepts]] defined in this document — the sections and productions marked 1.2 — is an editors' proposal that has not yet been reviewed or adopted by the Working Group. It is not, and does not define, a standard.

A machine-formal, bidirectional version of the syntax-to-triples mapping for the RDF 1.2 additions is being developed in the Shuttle grammar formalism [[rdf-shuttle]] and will be linked from this document when available.

An Example of the SHACL Compact Syntax

The following example illustrates key features of the SHACL Compact Syntax. It is an extended version of the Person Example from [[!shacl]]. 

BASE <http://example.com/ns>

IMPORTS <http://example.com/person-ontology>

PREFIX ex: <http://example.com/ns#>

shape ex:PersonShape -> ex:Person {
	closed=true ignoredProperties=[rdf:type] . 

	ex:ssn       xsd:string [0..1] pattern="^\\d{3}-\\d{2}-\\d{4}$" .
	ex:worksFor  IRI ex:Company [0..*] .
	ex:address   BlankNode [0..1] {
		ex:city xsd:string [1..1] .
		ex:postalCode xsd:integer|xsd:string [1..1] maxLength=5 .
	} .
}

Using the this example is mapped to the following Turtle RDF graph: 

@base <http://example.com/ns> .
@prefix ex: <http://example.com/ns#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix sh: <http://www.w3.org/ns/shacl#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

<http://example.com/ns>
	rdf:type owl:Ontology ;
	owl:imports <http://example.com/person-ontology> .

ex:PersonShape
	a sh:NodeShape ;
	sh:targetClass ex:Person ;
	sh:closed true ;
	sh:ignoredProperties ( rdf:type ) ;
	sh:property [
		sh:path ex:ssn ;
		sh:maxCount 1 ;
		sh:datatype xsd:string ;
		sh:pattern "^\\d{3}-\\d{2}-\\d{4}$" ;
	] ;
	sh:property [
		sh:path ex:worksFor ;
		sh:class ex:Company ;
		sh:nodeKind sh:IRI ;
	] ;
	sh:property [
		sh:path ex:address ;
		sh:maxCount 1 ;
		sh:nodeKind sh:BlankNode ;
		sh:node [
			sh:property [
				sh:path ex:city ;
				sh:datatype xsd:string ;
				sh:minCount 1 ;
				sh:maxCount 1 ;
			] ;
			sh:property [
				sh:path ex:postalCode ;
				sh:or ( [ sh:datatype xsd:integer ] [ sh:datatype xsd:string ] ) ;
				sh:minCount 1 ;
				sh:maxCount 1 ;
				sh:maxLength 5 ;
			] ;
		] ;
	] .

SHACL also supports a design pattern where shapes that are also declared to be classes apply to all instances of the class. The Compact Syntax includes the keyword shapeClass for this case, as shown in the snippet below: 

shapeClass ex:Person {
	...
}

Compared to the example further above using shape, this would produce the following RDF triples (with no sh:targetClass triple): 

ex:Person
	a sh:NodeShape, rdfs:Class ;
	...

The SHACL Compact Syntax can be used both as an exchange format but also as temporary editing input format. If SHACL Compact Syntax files are saved, the recommended file ending is .shaclc.

1.2 Support for RDF 1.2

RDF 1.2 [[rdf12-concepts]] introduces three features that are directly relevant to shape declarations:

  • Triple terms — RDF terms of the form <<( subject predicate object )>> that denote a triple and may occur in the object position of other triples;
  • Reifiers — nodes related to a triple term through the rdf:reifies property, providing the RDF 1.2 idiom for making statements about statements; Turtle 1.2 [[rdf12-turtle]] provides the reified-triple shorthand << s p o ~ r >> for them;
  • Directional language tags — language-tagged strings that additionally carry a base direction (ltr or rtl), written "..."@lang--dir and typed rdf:dirLangString.

SHACL 1.2 Core [[shacl12-core]] correspondingly adds the node kind sh:TripleTerm, list-valued sh:nodeKind, and the constraint component sh:ReifierShapeConstraintComponent with parameters sh:reifierShape and sh:reificationRequired, and admits rdf:dirLangString literals wherever language-tagged strings are admitted (e.g. sh:message, sh:name, sh:description).

This document extends the SHACL Compact Syntax so that these features can be written compactly. The extensions are conservative: every SHACL Compact Syntax document that is valid without the productions marked 1.2 remains valid and maps to the same triples.

Summary of RDF 1.2 Additions

Compact syntax form RDF 1.2 construct Mapping
VERSION "1.2" Version declaration (as in Turtle 1.2) No triples produced; declares the syntax version of the document
"text"@lang--ltr, "text"@lang--rtl Directional language-tagged string A literal with datatype rdf:dirLangString, the given language tag, and base direction ltr or rtl
<<( s p o )>> Triple term The triple term itself, used directly as the object of the triple being produced (e.g. as a value of sh:targetNode, sh:hasValue, or a member of an sh:in list); no additional triples produced
<< s p o ~ r >> Reified triple with reifier r Produces r rdf:reifies <<( s p o )>>; the value of the surrounding construct is r
TripleTerm (node kind) Triple-term node kind ?shape sh:nodeKind sh:TripleTerm
nodeKind=[IRI Literal TripleTerm] List-valued sh:nodeKind (SHACL 1.2) ?shape sh:nodeKind ( sh:IRI sh:Literal sh:TripleTerm )
reifierShape=ex:Shape or reifierShape={ … } Reifier shape constraint (SHACL 1.2) ?property sh:reifierShape ?shape, with the inline body mapped onto a new blank node shape
reificationRequired=true Required reification (SHACL 1.2) ?property sh:reificationRequired true

An Example with RDF 1.2 Features

The following example exercises each of the RDF 1.2 additions: a version declaration, a directional language tag in a message, the TripleTerm node kind, a triple term as a constraint value, a reified triple as a target, and a reifier shape. 

BASE <http://example.com/ns>
VERSION "1.2"

PREFIX ex: <http://example.com/ns#>

shape ex:PersonShape -> ex:Person {
	ex:age xsd:integer [1..1]
		reificationRequired=true
		reifierShape={
			ex:author IRI [1..1] .
			ex:date xsd:date [1..1] .
		}
		message="Age statements must carry provenance."@en--ltr .
}

shape ex:ReifierNodeShape {
	targetSubjectsOf=rdf:reifies .
	rdf:reifies TripleTerm [1..1] .
}

shape ex:MarriageShape {
	targetNode=<< ex:alice ex:marriedTo ex:bob ~ ex:m1 >> .
	rdf:reifies hasValue=<<( ex:alice ex:marriedTo ex:bob )>> .
	ex:since xsd:date [1..1] .
}

Using the mapping defined in this document, this example produces the following Turtle 1.2 [[rdf12-turtle]] graph:

@base <http://example.com/ns> .
@prefix ex: <http://example.com/ns#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix sh: <http://www.w3.org/ns/shacl#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

<http://example.com/ns> rdf:type owl:Ontology .

ex:PersonShape
	a sh:NodeShape ;
	sh:targetClass ex:Person ;
	sh:property [
		sh:path ex:age ;
		sh:datatype xsd:integer ;
		sh:minCount 1 ;
		sh:maxCount 1 ;
		sh:reificationRequired true ;
		sh:reifierShape [
			sh:property [
				sh:path ex:author ;
				sh:nodeKind sh:IRI ;
				sh:minCount 1 ;
				sh:maxCount 1 ;
			] ;
			sh:property [
				sh:path ex:date ;
				sh:datatype xsd:date ;
				sh:minCount 1 ;
				sh:maxCount 1 ;
			] ;
		] ;
		sh:message "Age statements must carry provenance."@en--ltr ;
	] .

ex:ReifierNodeShape
	a sh:NodeShape ;
	sh:targetSubjectsOf rdf:reifies ;
	sh:property [
		sh:path rdf:reifies ;
		sh:nodeKind sh:TripleTerm ;
		sh:minCount 1 ;
		sh:maxCount 1 ;
	] .

ex:m1 rdf:reifies <<( ex:alice ex:marriedTo ex:bob )>> .

ex:MarriageShape
	a sh:NodeShape ;
	sh:targetNode ex:m1 ;
	sh:property [
		sh:path rdf:reifies ;
		sh:hasValue <<( ex:alice ex:marriedTo ex:bob )>> ;
	] ;
	sh:property [
		sh:path ex:since ;
		sh:datatype xsd:date ;
		sh:minCount 1 ;
		sh:maxCount 1 ;
	] .

Grammar and Production Rules

The following grammar (in ANTLR format) defines the parsing rules for the SHACL Compact Syntax. Valid SHACL Compact Syntax documents must be parseable against this grammar, must not cause any errors during the application of the production rules and furthermore produce no ill-formed nodes. 

grammar SHACLC;

shaclDoc            : directive* (nodeShape|shapeClass)* EOF;

directive           : baseDecl | importsDecl | prefixDecl | versionDecl ;
baseDecl            : KW_BASE  IRIREF ;
importsDecl         : KW_IMPORTS IRIREF ;
prefixDecl          : KW_PREFIX PNAME_NS IRIREF ;
versionDecl         : KW_VERSION string ;

nodeShape           : KW_SHAPE iri targetClass? nodeShapeBody ;
shapeClass          : KW_SHAPE_CLASS iri nodeShapeBody ;
nodeShapeBody       : '{' constraint* '}';
targetClass         : '->' iri+ ;

constraint          : ( nodeOr+ | propertyShape ) '.' ;
nodeOr              : nodeNot ( '|' nodeNot) * ;
nodeNot             : negation? nodeValue ;
nodeValue           : nodeParam '=' iriOrLiteralOrArray
                    | nodeKindValue ;

propertyShape       : path ( propertyCount | propertyOr )* ;
propertyOr          : propertyNot ( '|' propertyNot) * ;
propertyNot         : negation? propertyAtom ;
propertyAtom        : propertyType | nodeKind | shapeRef | propertyValue | nodeShapeBody ;
propertyCount       : '[' propertyMinCount '..' propertyMaxCount ']' ;
propertyMinCount    : INTEGER ;
propertyMaxCount    : (INTEGER | '*') ;
propertyType        : iri ;
nodeKind            : 'BlankNode' | 'IRI' | 'Literal' | 'BlankNodeOrIRI' |
                      'BlankNodeOrLiteral' | 'IRIOrLiteral' | 'TripleTerm' ;
shapeRef            : ATPNAME_LN | ATPNAME_NS | '@' IRIREF ;
propertyValue       : propertyParam '=' iriOrLiteralOrArray
                    | nodeKindValue
                    | reifierShapeValue ;
negation            : '!' ;

nodeKindValue       : 'nodeKind' '=' ( nodeKindMember | nodeKindList ) ;
nodeKindList        : '[' nodeKindMember+ ']' ;
nodeKindMember      : nodeKind | iri ;

reifierShapeValue   : 'reifierShape' '=' ( iri | nodeShapeBody ) ;

path                : pathAlternative ;
pathAlternative     : pathSequence ( '|' pathSequence )* ;
pathSequence        : pathEltOrInverse ( '/' pathEltOrInverse )* ;
pathElt             : pathPrimary pathMod? ;
pathEltOrInverse    : pathElt | pathInverse pathElt ;
pathInverse         : '^' ;
pathMod             : '?' | '*' | '+' ;
pathPrimary         : iri | '(' path ')' ;

iriOrLiteralOrArray : iriOrLiteral | array ;
iriOrLiteral        : iri | literal | tripleTerm | reifiedTriple ;

tripleTerm          : '<<(' ttSubject predicate ttObject ')>>' ;
reifiedTriple       : '<<' ttSubject predicate ttObject reifier? '>>' ;
reifier             : '~' iri ;
ttSubject           : iri ;
predicate           : iri | KW_A ;
ttObject            : iri | literal | tripleTerm ;

iri                 : IRIREF | prefixedName ;
prefixedName        : PNAME_LN | PNAME_NS ;

literal             : rdfLiteral | numericLiteral | booleanLiteral ;
booleanLiteral      : KW_TRUE | KW_FALSE ;
numericLiteral      : INTEGER | DECIMAL | DOUBLE ;
rdfLiteral          : string (LANG_DIR | '^^' datatype)? ;
datatype            : iri ;
string              : STRING_LITERAL_LONG1 | STRING_LITERAL_LONG2 | STRING_LITERAL1 | STRING_LITERAL2 ;

array               : '[' iriOrLiteral* ']' ;

nodeParam           : 'targetNode' | 'targetObjectsOf' | 'targetSubjectsOf' |
                      'deactivated' | 'severity' | 'message' |
                      'class' | 'datatype' |
                      'minExclusive' | 'minInclusive' | 'maxExclusive' | 'maxInclusive' |
                      'minLength' | 'maxLength' | 'pattern' | 'flags' | 'languageIn' |
                      'equals' | 'disjoint' |
                      'closed' | 'ignoredProperties' | 'hasValue' | 'in' ;

propertyParam       : 'deactivated' | 'severity' | 'message' |
                      'class' | 'datatype' |
                      'minExclusive' | 'minInclusive' | 'maxExclusive' | 'maxInclusive' |
                      'minLength' | 'maxLength' | 'pattern' | 'flags' | 'languageIn' | 'uniqueLang' |
                      'equals' | 'disjoint' | 'lessThan' | 'lessThanOrEquals' |
                      'qualifiedValueShape' | 'qualifiedMinCount' | 'qualifiedMaxCount' | 'qualifiedValueShapesDisjoint' |
                      'closed' | 'ignoredProperties' | 'hasValue' | 'in' |
                      'reificationRequired' ;

// Keywords
KW_BASE             : 'BASE' ;
KW_IMPORTS          : 'IMPORTS' ;
KW_PREFIX           : 'PREFIX' ;
KW_VERSION          : 'VERSION' ;

KW_SHAPE_CLASS      : 'shapeClass' ;
KW_SHAPE            : 'shape' ;

KW_TRUE             : 'true' ;
KW_FALSE            : 'false' ;
KW_A                : 'a' ;

// Terminals
PASS                : [ \t\r\n]+ -> skip;
COMMENT             : '#' ~[\r\n]* -> skip;

IRIREF              : '<' (~[\u0000-\u0020=<>\"{}|^`\\] | UCHAR)* '>' ;
PNAME_NS            : PN_PREFIX? ':' ;
PNAME_LN            : PNAME_NS PN_LOCAL ;
ATPNAME_NS          : '@' PN_PREFIX? ':' ;
ATPNAME_LN          : '@' PNAME_NS PN_LOCAL ;
LANG_DIR            : '@' [a-zA-Z]+ ('-' [a-zA-Z0-9]+)* ('--' [a-zA-Z]+)? ;
INTEGER             : [+-]? [0-9]+ ;
DECIMAL             : [+-]? [0-9]* '.' [0-9]+ ;
DOUBLE              : [+-]? ([0-9]+ '.' [0-9]* EXPONENT | '.'? [0-9]+ EXPONENT) ;
fragment EXPONENT   : [eE] [+-]? [0-9]+ ;
STRING_LITERAL1     : '\'' (~[\u0027\u005C\u000A\u000D] | ECHAR | UCHAR)* '\'' ;
STRING_LITERAL2     : '"' (~[\u0022\u005C\u000A\u000D] | ECHAR | UCHAR)* '"' ;
STRING_LITERAL_LONG1: '\'\'\'' (('\'' | '\'\'')? (~[\'\\] | ECHAR | UCHAR))* '\'\'\'' ;
STRING_LITERAL_LONG2: '"""' (('"' | '""')? (~[\"\\] | ECHAR | UCHAR))* '"""' ;
fragment UCHAR      : '\\u' HEX HEX HEX HEX | '\\U' HEX HEX HEX HEX HEX HEX HEX HEX ;
fragment ECHAR      : '\\' [tbnrf\\\"\'] ;
fragment WS         : [\u0020\u0009\u000D\u000A] ;
fragment PN_CHARS_BASE: [A-Z] | [a-z] | [\u00C0-\u00D6] | [\u00D8-\u00F6] | [\u00F8-\u02FF] | [\u0370-\u037D]
                       | [\u037F-\u1FFF] | [\u200C-\u200D] | [\u2070-\u218F] | [\u2C00-\u2FEF] | [\u3001-\uD7FF]
                       | [\uF900-\uFDCF] | [\uFDF0-\uFFFD]
					   		   ;
fragment PN_CHARS_U : PN_CHARS_BASE | '_' ;
fragment PN_CHARS   : PN_CHARS_U | '-' | [0-9] | [\u00B7] | [\u0300-\u036F] | [\u203F-\u2040] ;
fragment PN_PREFIX  : PN_CHARS_BASE ((PN_CHARS | '.')* PN_CHARS)? ;
fragment PN_LOCAL   : (PN_CHARS_U | ':' | [0-9] | PLX) ((PN_CHARS | '.' | ':' | PLX)* (PN_CHARS | ':' | PLX))? ;
fragment PLX        : PERCENT | PN_LOCAL_ESC ;
fragment PERCENT    : '%' HEX HEX ;
fragment HEX        : [0-9] | [A-F] | [a-f] ;
fragment PN_LOCAL_ESC: '\\' ('_' | '~' | '.' | '-' | '!' | '$' | '&' | '\'' | '(' | ')' | '*' | '+' | ','
                       | ';' | '=' | '/' | '?' | '#' | '@' | '%') ;

The grammar is also available as a standalone file: SHACLC.g4.

The following notes apply to the productions marked 1.2:

  • 1.2 Lexing << and <<(. The IRIREF terminal excludes < from its body, so an input beginning << can never be the start of an IRI reference. Lexers must recognize <<( and )>> in preference to << and >> (longest match), exactly as in Turtle 1.2 [[rdf12-turtle]].
  • 1.2 LANG_DIR replaces LANGTAG. The terminal follows the Turtle 1.2 LANG_DIR production. When the '--' suffix is present, its value MUST be ltr or rtl (lowercase); any other value is a syntax error.
  • 1.2 Subjects of triple terms are IRIs. Unlike Turtle 1.2, the compact syntax provides no blank node label syntax, so ttSubject and reifier admit only IRIs. This is not a practical restriction for shapes graphs: a blank node in a shapes graph cannot co-refer with any node of a data graph, so blank-node subjects and reifiers would not produce useful targets or values.
  • 1.2 a as predicate. The keyword a is admitted only in the predicate position inside tripleTerm and reifiedTriple and maps to rdf:type, as in Turtle.
  • 1.2 nodeKind and reifierShape parameters. The parameter name nodeKind is removed from the nodeParam/propertyParam alternatives and handled by the dedicated nodeKindValue production; likewise reifierShape is handled by reifierShapeValue. Documents that used nodeKind=sh:IRI previously remain valid, since an iri is admitted as a nodeKindMember.

A parser for the SHACL Compact Syntax receives as input a (text) document plus an optional base URI which is used as initial value for the variable ?baseURI. The parser uses a prefix mapping which has initial mappings for the following namespaces:

Prefix Namespace
rdf: http://www.w3.org/1999/02/22-rdf-syntax-ns#
rdfs: http://www.w3.org/2000/01/rdf-schema#
sh: http://www.w3.org/ns/shacl#
xsd: http://www.w3.org/2001/XMLSchema#

It then produces a new RDF graph — an RDF 1.2 graph [[rdf12-concepts]] when the productions marked 1.2 are used — with the triples produced by the following rules.

baseDecl: set ?baseURI to the IRI specified by IRIREF.

importsDecl: add the IRI specified by IRIREF into a set ?imports.

prefixDecl: add to the prefix mapping a mapping from the prefix PNAME_NS (without the ':') to the namespace specified by IRIREF.

1.2 versionDecl: Produces no triples. The string value declares the syntax version of the document and, if present, MUST be "1.2". A document that uses any of the syntactic forms marked 1.2 SHOULD include a version declaration. Parsers that do not support the RDF 1.2 additions MAY reject documents with a version declaration of "1.2".

Once the whole document has been completed, produce a triple ?baseURI rdf:type owl:Ontology using the final value of baseURI. Report an error if baseURI has no value but imports is not empty. For each iri in imports, produce a triple ?baseURI owl:imports ?iri.

nodeShape: Produce a triple ?shape rdf:type sh:NodeShape where ?shape is derived from the iri using iri. Use ?shape as context shape for the targetClass and nodeShapeBody.

shapeClass: Produce the triples ?shape rdf:type sh:NodeShape and ?shape rdf:type rdfs:Class where ?shape is derived from the iri using iri. Use ?shape as context shape for the nodeShapeBody.

targetClass: For each iri, produce a triple ?shape sh:targetClass ?iri where ?iri is derived from iri.

nodeShapeBody: Handle each constraint using the context shape ?shape.

constraint: Handle each nodeOr or propertyShape using the context shape ?shape.

nodeOr: If there is more than one nodeNot, then produce an RDF list ?or where for each nodeNot, there is a new blank node, and that blank node is used as context shape for the nodeNot. Then produce a triple ?shape sh:or ?or. If there is only one nodeNot, handle the nodeNot using the context shape ?shape.

nodeNot: If there is a negation, produce a new blank node ?not and produce a triple ?shape sh:not ?not. Then handle the nodeValue using ?not as context shape. If there is no negation, handle the nodeValue using the context shape ?shape.

nodeValue: Produce a triple ?shape ?predicate ?object where ?predicate is the IRI produced by concatenating the sh namespace with string value of nodeParam (for example "minLength" becomes sh:minLength), and ?object is derived from the iriOrLiteralOrArray.

propertyShape: Using a new blank node ?property, produce a triple ?shape sh:property ?property. Produce a triple ?property sh:path ?path where ?path is the result of path. Use ?property as context shape for propertyCount and propertyOr.

propertyCount: If propertyMinCount is not "0", produce a triple ?property sh:minCount ?minCount using the xsd:integer derived from propertyMinCount as ?minCount. If propertyMaxCount is not "*", produce a triple ?property sh:maxCount ?maxCount using the xsd:integer derived from propertyMaxCount as ?maxCount.

propertyOr: If there is more than one propertyNot, then produce an RDF list ?or where for each propertyNot, there is a new blank node, and that blank node is used as context shape for the propertyNot. Then produce a triple ?property sh:or ?or. If there is only one propertyNot, handle the propertyNot using the context shape ?property.

propertyNot: If there is a negation, produce a new blank node ?not and produce a triple ?property sh:not ?not. Then handle the propertyAtom using ?not as context shape. If there is no negation, handle the propertyAtom using the context shape ?property.

propertyAtom: Use ?property as context shape for any of the child elements. For a nested nodeShapeBody, produce a new blank node ?node and use that as the context shape ?shape. Then produce a triple ?property sh:node ?node.

1.2 propertyType (updated): Let ?iri be the IRI derived from the propertyType using iri. If ?iri is one of the RDF datatypes supported by SPARQL 1.2 [[sparql12-query]] — which include the XSD datatypes supported by SPARQL 1.1 (such as xsd:string) together with rdf:langString and rdf:dirLangString — then produce a triple ?property sh:datatype ?iri, otherwise ?property sh:class ?iri.

1.2 nodeKind (updated): Produce a triple ?property sh:nodeKind ?nodeKind where ?nodeKind is the IRI produced by concatenating the sh namespace with the text value of nodeKind (e.g., sh:Literal). The admitted keywords now include TripleTerm, which maps to sh:TripleTerm [[shacl12-core]].

1.2 nodeKindValue: Each nodeKindMember maps to a term ?m as follows: a nodeKind keyword K maps to the IRI sh:K; an iri maps to the derived IRI. If the value is a single nodeKindMember, produce the triple ?shape sh:nodeKind ?m; ?m must then be one of the seven instances of sh:NodeKind (sh:BlankNode, sh:IRI, sh:Literal, sh:BlankNodeOrIRI, sh:BlankNodeOrLiteral, sh:IRIOrLiteral, sh:TripleTerm). If the value is a nodeKindList, produce a SHACL list ?list whose members are the ?m in document order, and produce the triple ?shape sh:nodeKind ?list; each member must then be one of sh:BlankNode, sh:IRI, sh:Literal, or sh:TripleTerm, per the SHACL 1.2 syntax rules for list-valued sh:nodeKind [[shacl12-core]].

1.2 reifierShapeValue: If the value is an iri, produce the triple ?property sh:reifierShape ?iri. If the value is a nodeShapeBody, produce a new blank node ?r, produce the triple ?property sh:reifierShape ?r, and handle the nodeShapeBody using ?r as the context shape. This parameter is only admitted within property shapes; per [[shacl12-core]], when a property shape has a value for sh:reifierShape, its sh:path value is constrained to an IRI (not a path expression). The parameter may be repeated to associate multiple reifier shapes.

1.2 reificationRequired: Handled by the unchanged propertyValue rule (concatenating the sh namespace with the parameter name): produce the triple ?property sh:reificationRequired ?object, where ?object must be a literal with datatype xsd:boolean.

shapeRef: Produce a triple ?property sh:node ?node where ?node is the IRI derived from the substring of shapeRef after the '@' character using iri.

propertyValue: Produce a triple ?property ?predicate ?object where ?predicate is the IRI produced by concatenating the sh namespace with the string value of propertyParam, and ?object is derived from the iriOrLiteralOrArray.

path: If there is more than one pathSequence, produce a new RDF list ?list where there is one list member for the paths derived from each pathSequence. Then produce a triple ?alt sh:alternativePath ?list where ?alt is a new blank node, and return ?alt. If there is only one pathSequence, return the path derived from pathSequence.

pathSequence: If there is more than one pathEltOrInverse, produce a new blank node RDF list ?list where there is one list member for the path derived from each pathEltOrInverse. Return ?list. If there is only one pathEltOrInverse, return the path derived from pathEltOrInverse.

pathEltOrInverse: If there is a pathInverse, produce a triple ?path sh:inversePath ?inverse where ?path is a new blank node and ?inverse is the path derived from pathElt. Return ?path. If there is only one pathElt, return the path derived from pathElt.

pathElt: Let ?primary be the path derived from pathPrimary. If pathMod does not exist, return ?primary. Otherwise, produce and return a new blank node ?path with one of the following triples: If pathMod equals "?" produce a triple ?path sh:zeroOrOnePath ?primary. If pathMod equals "+" produce a triple ?path sh:oneOrMorePath ?primary. If pathMod equals "*" produce a triple ?path sh:zeroOrMorePath ?primary.

pathPrimary: If iri exists, return the predicate derived from that IRI. Otherwise, return the path derived from path.

1.2 iriOrLiteralOrArray (updated): If there is an array, produce and return an RDF list where each iriOrLiteral is a member; members may be triple terms or reifiers derived from reified triples, per iriOrLiteral. Otherwise, return iriOrLiteral for iriOrLiteral.

1.2 iriOrLiteral (updated): If there is an iri, return the node derived from iri. If there is a literal, apply Turtle's parsing rules to turn the string literal into an RDF literal, as refined by rdfLiteral. If there is a tripleTerm, return the triple term derived from tripleTerm. If there is a reifiedTriple, return the reifier returned by reifiedTriple. Consequently, triple terms and reified triples may appear wherever a value is expected — in particular as values of targetNode=, hasValue=, and as members of in=[…] arrays — and the resulting term becomes the object of the produced triple (e.g. ?shape sh:targetNode ?term).

1.2 rdfLiteral: Let ?lex be the unescaped value of string. If neither LANG_DIR nor a datatype is present, return the literal ?lex with datatype xsd:string. If a datatype is present, return the literal ?lex with that datatype; it is an error for the datatype IRI to be rdf:langString or rdf:dirLangString, since those literals cannot be formed without a language tag. If LANG_DIR is present and contains no '--', return the language-tagged string ?lex with the given language tag (lowercased) and datatype rdf:langString. If LANG_DIR is present and contains '--', let ?lang be the part between the leading '@' and the '--' (lowercased) and ?dir be the part after the '--'; ?dir MUST be ltr or rtl. Return the directional language-tagged string with lexical form ?lex, language tag ?lang, base direction ?dir, and datatype rdf:dirLangString [[rdf12-concepts]].

1.2 tripleTerm: Let ?s be the IRI derived from ttSubject, ?p the IRI derived from predicate, and ?o the term derived from ttObject. Return the RDF 1.2 triple term composed of (?s, ?p, ?o). This rule produces no triples: a triple term is a term, and asserts nothing. Note that in RDF 1.2 a triple term may occur only in the object position of a triple; every position in which the grammar admits tripleTerm maps to an object position (including membership in RDF lists, where the member is the object of an rdf:first triple).

1.2 reifiedTriple: Let ?tt be the triple term composed from ttSubject, predicate, and ttObject as in tripleTerm. If the reifier is present, let ?r be the IRI derived from its iri; otherwise let ?r be a new blank node. Produce the triple ?r rdf:reifies ?tt and return ?r.

The rdf:reifies triple is produced in the shapes graph. With an explicit IRI reifier this both documents the intended referent of the reifier and gives constraints such as targetNode=<< s p o ~ r >> a well-defined value (r) that can co-refer with nodes in a data graph. An anonymous reified triple (without ~ r) yields a fresh blank node, which cannot match any node of a data graph; it is therefore rarely useful and SHOULD be avoided.

1.2 ttSubject: Return the IRI derived from iri.

1.2 predicate: If the token is a, return rdf:type. Otherwise return the IRI derived from iri.

1.2 ttObject: If there is an iri, return the derived IRI. If there is a literal, return the literal derived from rdfLiteral and the literal rules. If there is a tripleTerm, return the (nested) triple term derived from tripleTerm.

iri: If there is a IRIREF, return the result of IRIREF. Otherwise, return an IRI applying the current prefix mapping on prefixedName. Report an error if there is no matching prefix.

IRIREF: Return the IRI consisting of the substring of IRIREF between the leading < and the trailing >, turning relative IRIs into absolute IRIs using the current ?baseURI.

Developers may find the Test Cases useful. Each test consists of a .shaclc file and an associated .ttl file. Parsing the .shaclc file must produce a graph that is isomorphic to the .ttl file (Turtle 1.2 [[rdf12-turtle]] for the tests exercising the RDF 1.2 additions: directional-language, triple-term-values, and reifier-shape). The test cases are not normative.

1.2 Interaction with Existing Constraint Parameters

  • languageIn is unchanged: its members remain plain xsd:string basic language ranges per [[BCP47]]. Directional language-tagged values in the data graph are matched on their language tag only (the base direction does not participate in langMatches-style filtering) [[shacl12-core]].
  • uniqueLang is unchanged syntactically; note that under SHACL 1.2 the base direction of rdf:dirLangString values participates in the uniqueness condition, so "1"@ar--rtl and "1"@ar--ltr count as different languages [[shacl12-core]].
  • datatype= may name rdf:dirLangString to constrain values to directional language-tagged strings, e.g. ex:label datatype=rdf:dirLangString . (equivalently, the bare propertyType form ex:label rdf:dirLangString .).
  • pattern, minLength, maxLength apply to triple terms as to other non-literal values: a triple term has no lexical form, so such constraints produce validation results for triple-term value nodes, as defined by [[shacl12-core]].

Encoding considerations:
SHACL Compact Syntax (SHACLC) is a text language encoded in UTF-8.
Security considerations:

Revealing the structure of an RDF graph can reveal information about the content of conformant data. For instance, a schema with a predicate to describe cancer stage indicates that conforming graphs describe patients with cancer.

The process of testing a graph's conformance to a schema could draw significant system resources and be a vector for Denial of Service attacks.

RDF Turtle security considerations about IRI spoofing may also apply here.
